Internal Manual

The Loyaltymaster Design System

How any human or LLM turns a page brief into a production-ready Loyaltymaster page — the same look, every time, with zero invented design.

The 2-step process

0

Always start at llms.txt

llms.txt at the repo root is the single entry point. It states the Key Rule, routes you (or your LLM) to the right runbook for the task, and lists which folders are noise and must not be read.

1

Runbook A — brief → Markdown outline

Give the LLM a page brief, URL, or screenshot and point it at RUNBOOK_A_PAGE_TO_MARKDOWN_OUTLINE.md. It returns a strict Markdown outline: every section mapped to an approved registry component, with props, content fields, CTAs, and SEO fields filled in. No code is written in this step.

You review the outline. Nothing proceeds without your approval.

2

Runbook B — approved outline → production page

Hand the approved outline to RUNBOOK_B_MARKDOWN_OUTLINE_TO_PRODUCTION_PAGE.md. The LLM re-validates every component against the registry, then produces the Next.js page package: route file, page body, SEO route entry, and SitePage wiring — importing only from library/src/components/.

Run node scripts/validate-phase2.mjs afterwards and record your approval before publishing.

What lives where

  • registry/components.json — the only component inventory. 33 stable components with props, variants, slots, tokens, and paths. Never trust a component list written in prose.
  • tokens/design-tokens.json — the only token source. The CSS, TypeScript, and Tailwind files are generated from it.
  • specs/components/ — one rule file per component. Read the spec immediately before using a component; edited rules win.
  • library/src/components/ — the production React code. The only place runtime imports come from.
  • templates/ — approved composition recipes: which components, in which order, for each page type.
  • examples/ — approved patterns, blocked anti-patterns, and six full generated proof packages.
  • showcase/app — renders every component in a browser and runs the visual, interaction, and production-fidelity gates.

Hard boundaries

Never

  • Invent a component, variant, color, radius, shadow, font, or animation.
  • Add a navbar, header, or footer to a normal page body — production supplies the global shell. Pages are body-only by default.
  • Import runtime code from /Components/ (evidence only), from _archive/, from raw MagicPath output, or from the protected sendPUSH production repo.
  • Use a raw color or spacing literal when a token exists.

When something is missing

If no approved component can express what the brief needs, the workflow stops and files templates/new-component-request.md. The component is then designed, built, registered, gated, and approved by you — only after that can any page use it. No improvised substitutes, ever.

Why this system exists

Left alone, every LLM produces the same generic page: purple gradients, Inter on white, endless identical card grids. That is design drift — and after ten pages, Loyaltymaster would no longer look like Loyaltymaster.

This system prevents drift by treating design as a box of approved Lego bricks. An AI may pick bricks and arrange them by the recipes. It may never mold a new brick.

Three levels of rules

1

Brand rules

BRAND.md and DESIGN_SYSTEM.md — voice, audience, colors, typography, motion, and the anti-references to avoid. Rodger Bold for big promises, Onest for readability, yellow only for high-intent action moments.

2

Component rules

One spec per component in specs/components/: when to use it, when not to, allowed props and states, accessibility, and its exact tokens. The spec is editable — the current spec always wins over memory or old examples.

3

Combination rules

Templates in templates/ define which components go together and in what order for each page type — a trial page, a pricing page, a proof-led sales page. Composition is a recipe, not a free-for-all.

Design principles behind the workflow

Machine-readable beats prose

The component inventory, props, and tokens live in JSON that an LLM reads at runtime. Prose documents explain; they never define. This is why the registry — not any README — decides what exists.

Humans approve, machines verify

A human gate sits between outline and code, and before anything is published. Around that, scripts verify everything mechanically: file inventory, registry completeness, pixel-diff visual gates, interaction gates, and live-production fidelity comparison.

Fail closed

Every failure has a named stage (COMPONENT_NOT_APPROVED, TOKEN_INVALID, …). When the system can't do something correctly, it stops and reports — it never patches around the rules.

Proof over promises

Six generated example packages prove the whole workflow end-to-end: filled brief → body-only TSX → component evidence → checklist. Blocked examples document exactly what rejected drift looks like, so the LLM recognizes it.
